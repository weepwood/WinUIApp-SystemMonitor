## 3. P0 · 采样性能与数据正确性（收益最大）

### 3.1 CPU：3 次 WMI → 系统调用

每 1 秒 3 次 WMI 往返，是当前最大的常驻开销来源，且 `Win32_Processor.LoadPercentage` 只有整数精度、刷新粒度受 WMI 提供程序限制。

建议改为：

- 总使用率与每核心：`GetSystemTimes` + `NtQuerySystemInformation(SystemProcessorPerformanceInformation)`，一次拿到全部逻辑处理器内核态/用户态/空闲时间，自行做差值。微秒级调用，精度可到 0.1%。
- 当前频率：`CallNtPowerInformation(ProcessorInformation)` 取 `CurrentMhz`，或在设置里用「低频刷新」（每 10 s）单独取一次，不必每秒查。
- 保留 WMI 作为回退路径（老系统/异常时），用接口切换便于测试。

### 3.2 进程：批量枚举替代逐个开句柄

`Process.GetProcesses()` 每次为每个 PID 打开句柄，`process.Threads` 还会构造线程集合（300 进程时开销显著，2 秒档尤其明显）。

建议：

- 用 `NtQuerySystemInformation(SystemProcessInformation)` 一次调用返回所有进程的 `ImageName`、`UniqueProcessId`、`WorkingSetSize`、`ThreadCount`、`HandleCount`、`KernelTime`/`UserTime`，这正是 System Informer 类工具的做法。
- CPU 百分比仍在两次采样间做差，键用 **PID + 进程启动时间**（`CreateTime` 也在同一结构体里），避免 PID 复用。
- 字段分级：`ThreadCount`/`HandleCount`/`WorkingSet` 常驻；命令行、模块路径、签名等只在选中时按需读取（当前已是这个方向，可再收敛）。

### 3.3 快慢采样分离为两个调度器

当前快慢采样在同一个 `RefreshAsync` 的 `Task.Run` 里串行执行：碰到慢采样那一拍（进程枚举 + WMI），整条时间线被拖长，1 秒节奏抖动。

建议拆成两个独立循环（快 1/2/5/10 s，慢 2/5/10 s），各自维护生成号与丢弃策略；UI 侧只做「局部属性更新」，互不阻塞。

### 3.4 网络：补上 IPv6 与虚拟网卡过滤

`NetworkInterface.GetIPv4Statistics()` 只统计 v4，IPv6 流量完全不计入；回环/隧道网卡也会混进「主要适配器」的判断。

建议改用 `GetIfTable2` / `MIB_IF_ROW2.InOctets|OutOctets`（一次拿全部接口，含 v6），按 `InterfaceType` 与 `OperStatus` 过滤；速率仍做差值。

### 3.5 磁盘速率：性能计数器失败的可见降级

`Win32_PerfFormattedData_PerfDisk_LogicalDisk` 依赖 WMI 性能提供程序；服务被禁用或计数器损坏时，速度会永久为 0 且界面无提示（README 已记录该风险，但用户看不到）。

建议：改用 PDH（`PdhOpenQuery` + `\LogicalDisk(*)\Disk Bytes/sec`）并检测返回码；不可用时在磁盘页给出 InfoBar「实时速率不可用（性能计数器被禁用）」，而不是静默 0。

### 3.6 内存：`GlobalMemoryStatusEx` + `GetPerformanceInfo`

`Win32_OperatingSystem` + `Win32_PerfFormattedData_PerfOS_Memory` 两次 WMI 换来的数据，P/Invoke 两次即可得到且更及时（已提交/缓存/内核池）。同样保留 WMI 回退。

### 3.7 历史带上时间戳

`UsageHistory` 假设「等间隔采样点」，暂停/切档后横轴语义会漂移（README 已如实说明）。若后续做导出或长时间窗口，建议存 `(timestamp, value)` 对，横轴才能标注真实时间、支持抽稀与断点。

### 3.8 自适应采样

已有「最小化时暂停」。可再进一步（都可做成设置项）：

- 窗口不可见但未最小化（被其他窗口覆盖）时降频；
- 电池供电时慢采样降一档；
- 只对**当前激活页面**需要的指标做高频采样（例如停在设置页时，CPU 曲线并不需要 1 s 粒度）。

> 收益预估：P0 全部落地后，常驻 CPU 占用与每秒内存分配应有量级下降；需要在应用内加「自身开销」读数才能量化验证（见 6.4）。

## 4. P1 · 进程页体验（对标 System Informer / btop）

当前进程页功能骨架已经完整（筛选、四列排序、详情、导出），主要差距在**稳定性与信息密度**。

| 问题 | 现象 | 建议 |
| --- | --- | --- |
| 行跳动 | 按内存/CPU 排序时，每 2–5 秒行位置变化，选中项跟着跳 | 引入 btop 的 "cpu lazy" 思路：名次变化需超过阈值（如 5%）才重排；同时「跟随选中项」保持滚动位置 |
| 缺少层级 | 只看到扁平列表 | 进程树（`InheritedFromUniqueProcessId`），支持折叠；按应用分组（同一 exe 多进程聚合 CPU/内存） |
| 列固定 | 4 列写死 | 列显隐/宽度/排序方向持久化到 `MonitorPreferences`；至少补「用户」「命令行」「启动时间」 |
| 视觉标识 | 全是文字 | 进程图标（`SHGetFileInfo`）、系统/服务进程标记、高占用着色 |
| 操作能力 | 只能看和复制 | 右键菜单：结束进程（二次确认）、结束进程树、打开文件位置、复制路径、在线搜索；全部走权限失败提示 |
| 虚拟化 | `ListView` + 全量 `ObservableCollection` + 固定 `Height="420"` | 改为页面骨架 `Grid` 的行 `*` 填充 + `ItemsRepeater`/`ListView` 虚拟化；只在可见时枚举完整字段 |
| 搜索 | 每次按键重建列表 | 加 200–300 ms 防抖；支持 `pid:1234`、`>200MB` 这类轻量过滤语法 |

## 5. P1 · 硬件与电源扩展（注意权限边界）

| 能力 | 可行路径 | 权限/风险 |
| --- | --- | --- |
| GPU 使用率 / 显存 | PDH `GPU Engine`、`GPU Adapter Memory` 计数器（用户态） | 无需提权；计数器按引擎分组，需要聚合 |
| GPU 温度 / 功耗 / 风扇 | `LibreHardwareMonitorLib`（MPL-2.0）或厂商 SDK（NVML/ADL） | 部分需要管理员 + 内核驱动；应做成**可选依赖、默认关闭** |
| 电池健康 | WMI `root\wmi`：`BatteryStaticData`（设计容量/循环次数）、`BatteryFullChargedCapacity`（满充容量）、`BatteryStatus`（放电速率） | 用户态可读；部分设备不支持 |
| 电池剩余时间 | 已有 `BatteryLifeTime`，可同时展示「充至满电所需时间」`BatteryFullLifeTime` | 无需提权 |
| 温度/风扇（CPU/主板/硬盘） | LibreHardwareMonitor 驱动路径 | 参考 TrafficMonitor：默认关闭、明确风险提示、失败不影响主功能 |

**结论：** 温度类功能应当作为「插件/可选组件」而不是主程序默认能力——这是 TrafficMonitor 用崩溃事故换来的行业共识（其 README 明确提示硬件监控可能导致崩溃与系统假死）。

## 6. P2 · 可视化与数据

### 6.1 图表坐标轴与自适应性

- 现在所有图都是 0–100% 固定纵轴。网络（Mbps）、磁盘（MB/s）这类没有上限的指标应使用自适应纵轴，并参考 btop 的「自动缩放」策略（留 1.2 倍余量 + 平滑回落）。
- 若历史窗口扩展到小时级，需降采样（LTTB 或按像素聚合），否则 120 点以上曲线会变成噪声块。
- 时间轴模式（6.3 的 `(timestamp, value)`）可让「暂停 5 分钟」在图上呈现为断点而非被压平。

### 6.2 高对比度适配（现存的真实缺陷）

`UsageHistoryChart.UpdateThemeBrushes()` 只判断 `ActualTheme == Dark`，网格线/刻度/悬停气泡全是硬编码 ARGB。在 Windows 高对比度主题下，这些灰线会落在黑色背景上几乎不可见。

建议：用 `Application.Current.Resources["SystemColorWindowTextColor"]` 等系统色，或在检测到高对比度时整体切换到 `SystemControlForegroundBaseHighBrush`；`App.xaml` 的 `HighContrast` 字典目前只覆盖了强调色，图表是漏网之鱼。

### 6.3 可达性

- 悬停读数目前只有鼠标路径：需支持键盘（图表可获得焦点后 ←/→ 移动读数）与触摸（长按）。
- 数值每秒变化，不要放进 `LiveRegion` 播报，否则屏幕阅读器会被刷屏；只在「提醒触发」时播报一次。

### 6.4 自身开销可视 + 历史导出

- 在「系统信息」或「关于」中显示本应用自身的 CPU / 工作集（System Informer 有类似行）。这既是优化效果的验证手段，也是诚实的工程展示。
- 历史导出 CSV/JSON（参考 LibreHardwareMonitor 的日志、Glances 的 API），并可选把最近 N 分钟落盘，便于事后排查。

## 7. P2 · 信息架构与 Fluent 设计

1. **导航从 8 项收敛到 4–5 组**
   建议：总览 / 性能（`TabView`：CPU·内存·磁盘·网络·GPU）/ 进程 / 系统（系统信息·电源）/ 设置。
   Windows 11 任务管理器就是「进程 / 性能 / 启动 / 用户 / 详细信息 / 服务」的扁平结构，单页信息密度更高，切换成本更低。当前「CPU 页只有一张图和几个磁贴」显得空。
2. **设置页可检索**
   21 张设置卡已经接近需要搜索的规模：加顶部搜索框 + 分区锚点，并在每张卡片上显示「默认值」与「立即生效/需重启」。
3. **状态语言统一**
   空状态（等待首次采样）、降级（性能计数器不可用）、权限失败（路径/优先级不可访问）应有统一的 `InfoBar`/空状态组件，而不是散落在各页的文字。
4. **常驻入口（可选，需权衡依赖）**
   TrafficMonitor 的核心竞争力是任务栏/悬浮窗常驻。若要做，优先「托盘图标 + 迷你悬浮窗」，实现上可 `P/Invoke Shell_NotifyIcon`（零依赖）或 `H.NotifyIcon.WinUI`（新增 NuGet，与「不新增依赖」的既有约束冲突，需明确决定）。
5. **本地化**
   目前中文硬编码在 XAML 与 C#。WinUI 原生方案是 `.resw` + `x:Uid`，加「语言：跟随系统 / 简体中文 / English」设置项。这也是把项目做成可被外部复用/贡献的前提。

## 9. 建议路线图

**迭代 A（性能基线，1–2 天）**
1. CPU 采集换 `GetSystemTimes` + 每核心系统调用（WMI 回退）
2. 进程采集换 `NtQuerySystemInformation` 批量 + PID/启动时间键
3. 快慢采样拆两个调度器
4. 应用内「自身开销」读数（用于前后对比）
5. 抽出采样计算库 + 首批单元测试

**迭代 B（进程页与图表，2–3 天）**
6. 行稳定性（lazy 排序 / 跟随选中）+ 列显隐持久化
7. 进程树 + 图标 + 右键操作
8. 图表高对比度、自适应纵轴、键盘读数
9. 网络 IPv6 / 磁盘计数器降级提示

**迭代 C（可选扩展）**
10. GPU 使用率（PDH，免提权）→ 温度类可选插件
11. 电池健康/功率、历史导出
12. 设置搜索、本地化、托盘悬浮窗（视依赖决策）

## 10. 明确不建议做的

- **默认提权或加载内核驱动**：与「免管理员、无驱动」的定位冲突，且显著提高杀软误报与支持成本。
- **引入 ETW 全量会话**：信息量大但实现与兼容成本远超收益；PDH/系统调用已足够。
- **重写为第三方 UI 框架 / 大量引入组件库**：当前 Fluent 2 + WinUI 3 的视觉语言已经统一，重写只会带来回归。
- **为了「像任务管理器」而堆功能**：服务管理、启动项编辑等属于 Autoruns 领域，超出「本机监测」定位。
